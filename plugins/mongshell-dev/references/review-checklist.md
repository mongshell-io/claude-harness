# 리뷰 체크리스트 (`REVIEW.md`) — 형식 · 읽는 법 · 추가 · 정리 기준 (정본)

소비 프로젝트가 사고 · 실수에서 얻은 교훈 중 **diff 만 보고 해당 여부를 고를 수 있는 것**을 저장소 루트
`REVIEW.md` 에 모은다. 리뷰어(`code-reviewer`)는 변경마다 모든 항목을 보지 않고 **트리거가 맞는 항목만** 검사한다.
파일은 선택 계약이다 — 없는 프로젝트는 이 단계를 건너뛴다. 프로젝트의 `REVIEW.md` 에는 **항목만** 두고, 이 문서의
형식 · 기준을 다시 적지 않는다(한 줄 링크로 가리킨다).

## 파일 형식

표 한 개. 열은 넷 — `#` · `트리거` · `검사` · `근거`.

| 열 | 쓰는 것 |
|---|---|
| `#` | `R1`, `R2` … — 지운 번호는 다시 쓰지 않고 비워 둔다 |
| 트리거 | diff 에서 보이는 것 — 경로 glob 과(또는) 추가 · 변경된 줄의 식별자 · 패턴. 둘 다 적으면 둘 다 맞아야 한다 |
| 검사 | 트리거된 변경에서 확인할 질문 — 예/아니오로 판정할 수 있게 |
| 근거 | 그 항목을 만든 이슈 · PR · 사고 기록 · 결정 번호. 근거가 없으면 항목을 만들지 않는다 |

## 읽는 법 (리뷰어)

1. **기준 브랜치의 판을 읽는다** — `git show origin/main:REVIEW.md`. 작업 트리 · PR 브랜치의 판이 아니다. 검사받는 변경이
   검사 규칙을 고쳐 스스로를 통과시키지 못하게 하려는 것이다. `REVIEW.md` 를 고친 PR 의 새 항목은 머지된 뒤부터 적용된다.
2. 변경 파일 목록 · diff 를 각 항목의 트리거에 댄다.
3. 맞는 항목만 검사하고 리포트에 `트리거된 항목: R2 · R5` 처럼 번호를 적는다(없으면 「없음」, 파일이 없으면 「해당 없음」).
   위반은 다른 finding 과 같은 공통 분류 등급으로 올리고 항목 번호를 붙인다.

## 항목을 더하는 기준

- **같은 종류의 실수가 2개 이상 PR 에서 나왔거나**, 한 번이라도 운영 사고 · 사용자 명시 결정으로 이어졌을 때.
- **diff 에서 식별할 수 있을 때** — 경로 · 식별자 · 패턴으로 트리거를 적을 수 없으면 넣지 않는다.
- **기계 검사로 바꿀 수 있으면 그쪽이 먼저다** — 프로젝트의 검사 스크립트 · lint · 타입으로 막을 수 있으면 그것을 만들고
  체크리스트에는 넣지 않는다. 기계 검사가 생기면 그 항목은 지운다.
- **영역 운영 규약 전체를 옮기지 않는다** — 영역별 `CLAUDE.md` 는 리뷰어가 이미 읽는다. 체크리스트는 그중 「놓쳐서 실제로
  사고가 난 것」을 diff 트리거로 고르는 색인이다.

## 정리 원칙

- 커지기만 하지 않게 한다. 릴리스 즈음(또는 항목이 15개를 넘으면) 한 번씩 훑어 — 트리거된 적 없는 항목, 기계 검사로 옮겨 간
  항목, 코드가 바뀌어 트리거 경로가 사라진 항목을 지운다.

## 여러 프로젝트 공통 항목

둘 이상의 소비 프로젝트에서 같은 근거로 반복되는 항목이 생기면 이 문서 아래 「공통 항목」 표로 올리고, 각 프로젝트
`REVIEW.md` 에서는 지운다. 리뷰어는 공통 항목을 이 파일에서, 프로젝트 항목을 기준 브랜치의 `REVIEW.md` 에서 읽는다.
공통 항목의 번호는 `C1`, `C2` … 로 프로젝트 번호와 섞이지 않게 한다. 지금은 없다.
