# systematic-debugging

**근본원인을 찾기 전에는 고치지 않는다.** 증상만 덮는 수정은 실패로 본다.

루트 `CLAUDE.md` 상시 코어의 "디버깅 원칙"(증상 패치 전에 근본원인, 같은 증상에 fix 3회 실패 시 아키텍처 의심)이 원칙이고, 이 스킬은 그것을 실행하는 절차다.

> 출처: [obra/superpowers](https://github.com/obra/superpowers) 의 `systematic-debugging` 을 이 하네스에 맞게 옮겼다 (MIT — `${CLAUDE_PLUGIN_ROOT}/LICENSE.superpowers`).

## 언제 적용하는가

테스트 실패 · 운영 버그 · 예상과 다른 동작 · 성능 문제 · 빌드 실패 · 외부 연동 문제 — 기술적 문제 전부.

**특히 이럴 때** 건너뛰고 싶어지지만 더 지켜야 한다:
- 급할 때 (급하면 추측하고 싶어진다 — 추측하며 헤매는 것보다 이 절차가 빠르다)
- "한 줄만 고치면 될 것 같을" 때 (단순한 버그에도 근본원인은 있다)
- 이미 수정을 몇 번 시도했는데 안 됐을 때
- 문제를 완전히 이해하지 못했을 때

상황이 트리거인 규율 스킬이라 명시 호출 없이 적용한다 (하네스 README "호출 방식").

## 절차

앞 단계를 끝내야 다음 단계로 간다.

### 근본원인 조사 (수정 전에 반드시)

1. **오류 메시지를 끝까지 읽는다** — 경고도 건너뛰지 않는다. 스택 트레이스 전체, 줄 번호, 파일 경로, 오류 코드.
2. **안정적으로 재현한다** — 정확한 단계는? 매번 일어나는가? 재현이 안 되면 추측하지 말고 데이터를 더 모은다.
3. **최근 변경을 본다** — `git diff`, 최근 커밋, 의존성·설정 변경, 환경 차이.
4. **여러 구성요소를 지나는 문제면 경계마다 계측한다** — 각 경계에서 들어온 값 · 나간 값 · 설정/환경 전파를 한 번에 찍고, 한 번 실행해 **어디서** 깨지는지 증거로 좁힌 다음 그 구성요소만 판다.
5. **데이터 흐름을 거꾸로 따라간다** — 잘못된 값은 어디서 왔나? 누가 그 값으로 불렀나? 출처까지 올라가 출처에서 고친다.

### 패턴 비교

1. 같은 코드베이스에서 비슷하게 **동작하는** 코드를 찾는다.
2. 참고 구현이 있으면 훑지 말고 **끝까지** 읽는다.
3. 동작하는 쪽과 깨진 쪽의 차이를 아무리 작아도 전부 적는다 — "그건 상관없을 것" 이라고 미리 지우지 않는다.
4. 그 코드가 기대는 설정 · 환경 · 전제를 확인한다.

### 가설과 검증

1. **가설은 하나만** — "X 가 원인이다, 왜냐하면 Y" 로 구체적으로 적는다.
2. **가장 작은 변경으로 검증한다** — 한 번에 변수 하나.
3. 맞으면 다음 단계로. 틀리면 **새 가설**을 세운다 — 틀린 수정 위에 수정을 쌓지 않는다.
4. 모르겠으면 "X 를 이해하지 못했다" 고 말한다. 아는 척하지 않는다.

### 수정

수정과 재현 테스트 작성은 루트 `CLAUDE.md` 오케스트레이터 규칙을 따른다 — 메인 세션은 조사·가설까지 하고, 실질 수정은 developer 에 위임한다(자명한 변경은 직접). 위임할 때 확인한 근본원인과 증거를 함께 넘긴다.

1. **실패부터 고정한다** — 가장 단순한 재현 수단(자동 테스트 · 테스트 체계가 없으면 일회성 스크립트 · 빌드 실패면 빌드 명령 그 자체)으로 수정 전에 실패하는 것을 확인한다. 자동 테스트로 만들 수 있으면 회귀 테스트로 남긴다.
2. **근본원인 하나만 고친다** — "온 김에" 개선 · 묶음 리팩토링 금지.
3. **확인한다** — 그 테스트가 통과하고, 다른 테스트가 깨지지 않았고, 원래 증상이 실제로 사라졌는지. 완료 주장은 `verification-before-completion` 스킬을 따른다.
4. **수정이 안 먹으면 멈춘다** — **같은 증상**에 대한 수정 시도를 센다. 3회 미만이면 새 정보를 들고 근본원인 조사로 돌아간다. **3회 이상이면 네 번째 수정을 시도하지 않는다** — 아래로.

> `/plan` 루프 안에서는 `/plan` 의 iteration · Round 상한이 진행 여부를 정하고, 이 스킬은 각 시도 안의 절차만 정한다. 같은 증상에 3회 실패한 developer 는 다음 수정을 하지 않고 REPORT 비고에 "같은 증상 3회 실패 — 구조 의심" 과 시도·증거를 적어 메인 세션에 넘긴다.

### 세 번 실패했다면: 구조를 의심한다

이런 패턴이면 가설이 틀린 게 아니라 구조가 틀린 것이다:
- 고칠 때마다 다른 곳에서 새 공유 상태 · 결합 · 문제가 드러난다
- 고치려면 "대규모 리팩토링" 이 필요하다
- 고칠 때마다 다른 곳에 새 증상이 생긴다

이때는 수정을 멈추고, 지금까지의 시도와 증거를 정리해 사용자에게 알린다. 구조 판단이 필요하면 `architect` 에이전트 자문을 권고한다.

## 멈추고 처음으로 돌아갈 신호

- "일단 빨리 고치고 원인은 나중에"
- "X 를 바꿔 보고 되나 보자"
- "여러 개 한꺼번에 바꾸고 테스트 돌리자"
- "테스트는 건너뛰고 손으로 확인하자"
- "아마 X 일 테니 고치자"
- 데이터 흐름을 따라가기 전에 해결책부터 나열할 때
- 이미 2회 실패했는데 "한 번만 더"

## 사용자가 보내는 신호

- "그거 실제로 일어나는 거 맞아요?" — 확인 없이 가정했다
- "그러면 ~가 보이나요?" — 증거 수집을 했어야 했다
- "추측 그만" — 이해 없이 수정을 제안하고 있다
- "막힌 거죠?" — 지금 접근이 안 통하고 있다

이런 말이 나오면 근본원인 조사로 돌아간다.

## "근본원인이 없다" 는 결론

조사해 보니 정말로 환경 · 타이밍 · 외부 요인이라면: 무엇을 조사했는지 적고, 알맞은 처리(재시도 · 타임아웃 · 오류 메시지)를 넣고, 다음 조사를 위한 로그를 남긴다. 다만 "원인 없음" 의 대부분은 조사를 덜 한 것이다.

## 흔한 핑계

| 핑계 | 실제 |
|---|---|
| "간단한 문제라 절차가 필요 없다" | 간단한 문제엔 절차도 빨리 끝난다 |
| "급해서 절차를 밟을 시간이 없다" | 추측하며 헤매는 것이 더 느리다 |
| "고친 걸 확인한 뒤 테스트를 쓰겠다" | 테스트 없는 수정은 남지 않는다 |
| "여러 개 동시에 고치면 시간이 준다" | 무엇이 효과였는지 가를 수 없고 새 버그가 생긴다 |
| "문제가 보이니 바로 고치겠다" | 증상을 본 것과 원인을 이해한 것은 다르다 |
